# 8 x RTX 3090 (octo) profiles

Status: **untested / community-validated**. These profiles target eight homogeneous 24 GB sm_86 cards. No qualifying eight-card Merlin run was found in the retained evidence. Every pin, block count, pool and resident fit below is an **untested registry estimate**, not a measured result.

The profiles live in `tools/merlin/profiles/flash-next.json`, and `registry.py` generates the launchers in `tools/merlin/launchers/`. Registry consistency tests do not independently validate the capacity model. The original probe and its inputs/results are not distributed here. Numeric provenance and measurement limits are in [hardware-matrix.md](hardware-matrix.md#where-the-numbers-come-from).

| `fn-octo-3090-tp4pp2` (latency alternative) | TP4 x PP2 + EP, 25/23 | 12.19 GiB (13,088,912,835 B) | 16,515,072 B | 792 | 2,962,227 | 11 / 20 | 20 |

The registry's pool arithmetic is `floor((blocks - 1) x 262,144 / D)`, with stored denominators of 72 for TP2 x PP4 and 70 for TP4 x PP2. This reproduces the stored estimates but does not establish physical fit. Admission caps are scheduler settings; the default's cap of 32 does not promise 32 resident long-context sessions.

TP2 x PP4 is the capacity-oriented default because the model has two KV heads: TP4 duplicates them while PP4 reduces layers per card. TP4 x PP2 is the latency alternative. Neither relative performance nor the memory budget has been measured on eight cards.

## What the generated launchers contain

Both profiles use the same renderer as the reference quad. The following are software settings:

- `--kv-cache-memory-bytes "$KV_BYTES"`: override the estimated per-card pin after a pool-only boot;
- `--mamba-cache-mode align` (deprecated on vLLM 0.33 and without effect: Mamba prefix caching follows `--enable-prefix-caching`; the launchers still pass it and the server logs one warning);
- Flash-Next FGPC is off: no `--enable-mamba-shared-prefix-checkpoint`;
- the default image cap is 8,388,608 pixels; image headroom on eight cards is untested;
- the retired `VLLM_E2_*` switches (`PLE_PULL_TRANSPORT`, `SIDE_CACHE_LAYOUT`, `MAMBA_RETAIN_CHECKPOINT`, `GUARD_IDLE`) and `VLLM_ATTENTION_BACKEND` are not exported.

## Launch

Run from the repository root on Linux with Bash, after building this checkout for sm_86, installing its serving environment in `venv/`, and making the Flash-Next recipe assets available under `models/flash-next/`. The scales sidecar must match the checkpoint and release; the launcher checks its presence. The draft head scores the full vocabulary (`DRAFT_HEAD=bf16|int8|int4`, default `bf16`); reduced draft vocabulary was removed in 3.0.1, and `REDUCED_DRAFT_VOCAB` or `DRAFT_VOCAB` set in the environment stops the launch (an empty value, or `REDUCED_DRAFT_VOCAB=0`, is accepted). A source checkout alone is insufficient.

```bash
test -f vllm/__init__.py                                  # the built tree (TREE defaults to this checkout)
test -x venv/bin/python && test -x venv/bin/vllm          # the serving venv (VENV defaults to <checkout>/venv)
test -f models/flash-next/scales/qsa_kv_scales_262k.json  # the scales sidecar (SCALES overrides it)
venv/bin/python tools/merlin/preflight.py

mkdir -p scripts
venv/bin/python tools/merlin/preflight.py --emit launcher --profile fn-octo-3090-tp2pp4 > scripts/serve-octo-3090-tp2pp4.sh
bash scripts/serve-octo-3090-tp2pp4.sh /path/to/Qwen3.8-Flash-Next-W4A16-Merlin
```

The generated file is the shim checked in as `tools/merlin/launchers/serve-octo-3090-tp2pp4.sh`, which can be run directly. A shim finds the checkout by walking up from its own directory to the one holding `tools/merlin/launch.py` (`MERLIN_HOME` overrides that); `TREE`, `VENV`, `CACHE_ROOT` and `SCALES` override the launcher's defaults. Invoke the redirected file with `bash`; redirection does not make it executable. To use the latency alternative, substitute `fn-octo-3090-tp4pp2` and its output filename in the generation and invocation commands. A test runs this generation and the shim from `scripts/`, but an end-to-end eight-card launch has not been tested.

List `CUDA_VISIBLE_DEVICES` in pipeline order with each tensor-parallel group sharing the best link. For the default order `0..7`, the TP2 pairs are (0,1), (2,3), (4,5), (6,7).

## P2P

`P2P=on` is the default. It uses the reference interconnect settings and clears inherited `NCCL_P2P_DISABLE` and `NCCL_ALGO`.

`P2P=off` is an **explicit, untested, manual option**. The renderer sets `NCCL_P2P_DISABLE=1`, `NCCL_ALGO=Ring`, `NCCL_PROTO=LL128` and `--disable-custom-all-reduce`. These are configuration choices, with no qualifying eight-card measurement in the reviewed evidence.

## If the first boot fails

Record the error, failing rank, partition, pin and logged pool. Reduce `KV_BYTES` or evaluate a different partition with a fresh probe and boot; no alternative pin or resulting fit is established here. The previous four-card PP4 smoke, partition and pool claim has been removed because no qualifying record was found. A four-card stand-in would not establish the eight-card memory budget.

## Remaining acceptance

Both profiles need a pool-only boot, peak-memory measurement, decode at the checklist's context depths, needle results and smoke results on eight cards. See [Reporting a run](hardware-matrix.md#reporting-a-run-the-community-validation-checklist). Until then both remain **untested / community-validated**.
